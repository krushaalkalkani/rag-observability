Trace it. Measure it. Gate it.

Building a RAG system is about 30% of the work. The rest is knowing whether it works, why it fails, and fixing it fast. This adds that layer to a RAG system over SEC 10-K filings: every request traced, quality tracked over time with alerts, and a CI gate that blocks pull requests that make answers worse.

How it fits together

1 · Tracing every step

Each question becomes one trace; each pipeline stage is a span that records what a debugger needs. Open any request and you see exactly what was retrieved, how the re-ranker reordered it, what was sent to the LLM, and what came back.

The Anthropic SDK emits its own trace span, and Langfuse's default price for it ignored the thinking tokens Haiku bills as output: 238 output tokens instead of 816 on one request. Cost is now computed from a pricing table in config, and only the pipeline's own spans are exported.

2 · Quality over time

A monitoring job pulls finished traces into a metrics table, grades a stable 10% sample for faithfulness with an LLM judge (no ground truth needed), and checks alert rules. Thresholds were set from a 90-request baseline, not guessed.

3 · Incident 001: the regression no alert caught

The drill: ship a plausible change, then find it using only the dashboard and traces. The change was retrieval.top_k: 5 → 2, "to cut LLM input tokens". It did. Answers got worse, and every online quality metric improved.

Coverage and faithfulness ask "is what the model said supported?" With fewer chunks it said less, all of it supported. Neither metric can see what was left out.

  1. 18:31
    Bad change deployed

    Commit 6fa88a5, config 88336cc9e2fd. No errors, cost halved.

  2. 18:37
    Monitoring runs: zero alerts

    The detection gap: online metrics measure support, not completeness.

  3. 18:40
    Root cause confirmed

    Dashboard → per-config split → two traces of the same question. 6.7 minutes after the monitoring run.

  4. 18:41
    Rolled back

    config_hash returned to the healthy value, proving the config is identical, not just "reverted". Replay: 16/17 again.

The CI gate below is the fix: it measures retrieval against known answers on every PR, where this change drops below its threshold. Full postmortem.

4 · Gating every pull request

Each PR runs the golden-set eval in GitHub Actions and is compared with the latest baseline from main. Comparing to main catches what fixed floors miss: 0.99 → 0.88 clears an 0.85 floor but is an 11-point regression.

Every eval report records prompt_version, a hash of the prompt file, config_hash and git_sha; the gate warns when a prompt is edited without bumping its version.

What went wrong

  • The regression made the dashboard look better

    Groundedness metrics can't see missing information. Detection came from a cost step change; the real catch is retrieval measured against known answers in CI.

  • The dashboard could only compare prompt versions

    Incident 001 was a config change, invisible there. Fixed mid-incident: compare by prompt, config or commit.

  • An alert blamed an innocent commit

    During the outage the error alert's clue pointed at the newest commit, a dashboard-only change that happened to be running. The error messages said "network". Clues show correlation, not cause.

  • One NaN poisoned an average

    The RAGAS judge returned NaN for two answers, turning a mean into NaN. Failed grades now count as judge errors, and the PR comment says how many.
